IoT Sentinel

Detecting attacks on IoT networks without relying on labels: a two-stage intrusion detection system built as an MEng capstone, and the reproducible data pipeline I own inside it.

Why IoT needs this

IoT devices run stripped-down firmware, are rarely patched, and cannot host a security agent. The network is often the only place to observe them. Signature-based detection catches known attacks; an anomaly detector trained on traffic without attack labels can flag behaviour nobody has written a signature for, at the price of many false alarms.

The capstone combines both. Stage one, unsupervised, casts a wide net over packet-level traffic. Stage two, supervised, re-checks each alert using flow-level features. An alert survives only if both stages agree, which targets the problem a SOC analyst actually has: too many alerts to review.

System design

My part: the data pipeline

CIC IoT-DIAD 2024 is large: millions of packet and flow records across dozens of attack types, distributed as many separate files. Every model in the project depends on how that data is sampled and cleaned, so I built the preparation stage as a reproducible pipeline: one central configuration, one global random seed that every stochastic step derives from, and a JSON report written by every stage.

  1. SamplingA seeded, stratified sample of the packet-level data: 50,000 benign packets and up to 5,000 per attack category, across 27 attack categories in 7 attack families. Result: 181,336 rows and 139 columns.
  2. Exploratory analysisData types, memory footprint (366 MB in memory), missing values (49 columns affected, up to 96.9% missing in one), constant and near-constant features, and duplicated feature pairs, all written to machine-readable reports and figures.
  3. CleaningRemoved two constant columns, dropped one mostly empty column, imputed IP addresses by mode and numeric gaps by median, and checked for infinite values and duplicate rows (none found). 139 columns became 136.
  4. ScalingOutliers clipped, then StandardScaler, chosen because the autoencoder's reconstruction error and k-means distances are both dominated by whichever feature has the largest scale.
  5. Feature selectionA variance filter (threshold 1e-5) followed by a correlation filter at |r| > 0.95. Of 132 candidate features, 53 were redundant; 79 remain. The run takes about 8 seconds.

Most of the redundancy came from rolling-window statistics computed at several window lengths, and from pairs such as per-IP and per-IP-and-MAC variances that were identical in this data. Removing them matters most for k-means, where duplicated features silently double-weight one signal.

Team results

These numbers come from the team's evaluation in the final report. Stage 2 and the cascade were built by teammates; I report them because they show what the system achieved, not as my individual work.

0.789Stage 1 ROC-AUC on packet-level data (flow-level: 0.739)
0.967Stage 2 XGBoost ROC-AUC on flow features, F1 0.770
91.9%fewer false positives after the cascade: 8,195 down to 665
0.519cascade precision, up from 0.083 for Stage 1 alone

Detection rates varied sharply by attack: volumetric HTTP floods were caught in over 91% of cases, while XSS and brute force, which barely change packet statistics, were caught far less often. That pattern is the honest limit of unsupervised packet-level detection, and the reason Stage 2 exists.
