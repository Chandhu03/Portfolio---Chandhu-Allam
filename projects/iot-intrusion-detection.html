IoT Intrusion Detection System

Machine learning based intrusion detection system developed using IoT network traffic to identify malicious behavior and improve network security.

Applied project Machine learning Network security
GitHub ↗
⌁ Network defence

01 — Overview

Overview

This project builds an intrusion detection system for Internet of Things networks using machine learning applied to network traffic. Rather than matching packets against a list of known signatures, the system learns what ordinary device communication looks like and flags the traffic that departs from it.

IoT is a useful setting for this approach precisely because the devices are so predictable. A sensor that reports to one endpoint on a fixed interval has a narrow behavioural envelope, which makes deviation more meaningful than it would be on a general-purpose network full of human users.

The property that makes IoT devices hard to secure — minimal, fixed-function firmware you cannot patch or instrument — is the same property that makes their traffic easy to model.

02 — Problem

Problem statement

IoT deployments are difficult to defend from the inside. Devices ship with constrained processors and memory that cannot host a security agent, they are frequently deployed with default credentials, and firmware updates are slow or entirely absent. Compromised devices are then used as a foothold — for lateral movement, for scanning, or as botnet capacity.

Because the endpoint itself cannot be instrumented, the network becomes the only viable observation point. The problem is to detect compromise from traffic alone, on devices that offer no telemetry of their own, and to do so without generating an alert volume that nobody will act on.

03 — Objectives

Objectives

  • Work from IoT network traffic alone, assuming no agent, no logs, and no cooperation from the device.
  • Engineer flow-level features that describe communication behaviour — timing, volume, direction, and endpoint diversity — rather than payload contents.
  • Train and compare classifiers to distinguish benign device traffic from malicious activity.
  • Evaluate against realistic imbalance, since attack traffic is a small fraction of what a network actually carries.
  • Keep the feature set computable in near real time, so the approach remains viable outside a batch experiment.
  • Understand which features drive detection, so the output can be explained to whoever has to respond to it.

05 — Ownership

My role

I built this project end to end. That covers dataset selection and validation, converting raw captures into flow records, designing and testing the feature set, training and tuning the candidate models, designing an evaluation that survives class imbalance, and interpreting which signals the models were actually relying on.

The decisions I spent most time on were not the modelling ones. Choosing which features to compute — and rejecting the ones that turned out to leak label information — determined the quality of everything downstream.

06 — Approach

Implementation summary

  • Dataset review. Examine the capture for label balance, device coverage, and any artefact that would let a model cheat.
  • Flow extraction. Aggregate packets into bidirectional flows keyed by endpoint and protocol, which is the unit the model reasons about.
  • Feature engineering. Derive behavioural descriptors — inter-arrival timing, byte and packet counts per direction, connection duration, endpoint fan-out.
  • Leakage audit. Remove identifiers such as raw addresses and ports that would let a classifier memorise the attack instead of learning the behaviour.
  • Baseline and comparison. Fit an interpretable baseline first, then compare tree-based and ensemble classifiers under identical splits.
  • Imbalance-aware evaluation. Report precision, recall, and confusion structure per class rather than a single accuracy figure.
  • Feature attribution. Inspect feature importance to confirm the model is keyed to plausible behaviour, not an artefact.

07 — Friction

Challenges

Feature leakage

Early feature sets included fields that correlated with how the capture was produced rather than with attacker behaviour. Results looked excellent for the wrong reason, and finding that was a genuinely useful failure.

Class imbalance

Attack flows are heavily outnumbered by benign ones. Without imbalance-aware evaluation, a model that never predicts an attack still scores well.

Generalising to unseen devices

A model fitted to a specific set of devices learns those devices. Whether it transfers to hardware absent from training is a much harder question than test-set performance suggests.

Deployment constraints

Features that are cheap to compute over a completed capture are not necessarily cheap to compute on a live stream at line rate with bounded memory.

08 — Takeaways

Key learnings

  • Suspiciously good results deserve suspicion. The most valuable step in the project was investigating why an early model performed too well.
  • Features carry more weight than model choice. Time spent on what to measure paid off more than time spent on which algorithm to use.
  • Accuracy is the wrong headline metric whenever the classes are imbalanced and the error costs are asymmetric.
  • Test-set performance is not deployment performance. Device diversity, drift, and live latency all sit outside the experiment.
  • Detection has to be actionable. An alert that an operator cannot interpret or triage is not a security control.

09 — Next

Future improvements

  • Real-time inference at the edge — run detection on a gateway with realistic memory and latency budgets.
  • Cross-device validation — hold out entire device types from training to measure genuine generalisation.
  • Concept drift monitoring — detect when live traffic has moved away from the training distribution and flag retraining.
  • Adversarial evaluation — test whether traffic can be shaped to evade detection while still achieving the attacker's goal.
  • Alert enrichment — pair each detection with the contributing features so responders get context, not just a verdict.
