SecureText

Secure communication application implementing authentication, encryption, and secure software engineering principles.

⌇ Secure messaging

01 — Overview

Overview

SecureText is a communication application built around the idea that security is an architectural decision, not a feature added near the end. Authentication, message confidentiality, and safe handling of secrets were treated as requirements from the first commit rather than as hardening applied to a finished product.

The point of the project was as much about process as about the application. It was an exercise in applying secure software engineering practice deliberately — choosing vetted primitives, reasoning about what an attacker can reach, and being able to justify each security decision rather than copying a pattern.

The most useful discipline the project enforced: never implement a cryptographic primitive yourself. Selecting, configuring, and correctly using a reviewed library is the actual engineering work.

02 — Problem

Problem statement

Most messaging applications are built for delivery first, with security retrofitted once the product works. The result is predictable: credentials stored in a recoverable form, transport encryption that stops at the server boundary, keys handled as ordinary configuration, and no clear statement of what the system actually protects against.

The failures are rarely in the cryptography itself. They are in everything around it — session handling, key storage, password hashing choices, error paths that leak information, and dependencies nobody audited. SecureText addresses the problem of building a communication tool where those surrounding decisions are made deliberately and can be explained.

03 — Objectives

Objectives

  • Authenticate users safely, storing credentials with a slow, salted password hashing function rather than a general-purpose digest.
  • Encrypt message content using established, well-reviewed cryptographic libraries and no custom primitives.
  • Handle keys and secrets deliberately, keeping them out of source control, logs, and error output.
  • Manage sessions defensively, with explicit expiry and invalidation rather than indefinite tokens.
  • Validate all input at trust boundaries, treating anything arriving from a client as hostile until proven otherwise.
  • Write down the threat model — state plainly what the application defends against and, just as importantly, what it does not.

04 — Stack

Technologies used

Python

Application logic, message handling, and server-side components.

Vetted crypto library

Established encryption and key derivation implementations — no hand-rolled primitives.

Password hashing

A slow, salted algorithm chosen specifically to resist offline cracking.

TLS

Transport protection so credentials and content are never sent in the clear.

Relational storage

Parameterised queries throughout to eliminate injection at the data layer.

Git

Version control with secrets kept out of history by design.

05 — Ownership

My role

I designed and built SecureText myself. That covers the architecture, the authentication and session model, the encryption approach, the data layer, and the security review of my own work — including going back and changing decisions that did not hold up once I reasoned about them properly.

Reviewing your own code adversarially is an awkward skill to practise. Working through the application asking "how would I attack this" produced more useful changes than adding features would have.

06 — Approach

Implementation summary

  • Threat model first. Identify assets, trust boundaries, and realistic attackers before writing application code.
  • Authentication layer. Registration and login built on salted, computationally expensive password hashing with uniform failure responses.
  • Session management. Tokens generated from a cryptographically secure source, scoped, expiring, and invalidated on logout.
  • Message protection. Content encrypted through a vetted library with correct mode and nonce handling rather than defaults chosen by habit.
  • Data layer discipline. Parameterised queries everywhere and least-privilege database access.
  • Input validation. Every client-supplied value validated at the boundary, with errors that reveal nothing about internal state.
  • Self-review pass. A deliberate adversarial walkthrough of authentication, key handling, and error paths before considering the work finished.

07 — Friction

Challenges

Key management

Encrypting data is straightforward; deciding where keys live, how they are derived, and what happens when one is lost is where the genuine difficulty sits.

Correct use of primitives

A well-reviewed library is still easy to misuse. Getting modes, nonces, and key derivation right required reading the documentation properly rather than copying a snippet.

Usable security

Controls that make an application unpleasant to use get worked around. Balancing session expiry against user frustration was a real design tension.

Keeping secrets out of the repository

Configuration, test fixtures, and error logs all want to capture values that must never be committed. Preventing that needed conscious structure from the start.

08 — Takeaways

Key learnings

  • Never write your own cryptography. The engineering is in selecting and correctly configuring reviewed implementations.
  • Security added late is security that does not fit. Retrofitting authentication or encryption forces compromises that early design avoids entirely.
  • An unstated threat model is an untested one. Writing down what the system does not defend against is as valuable as listing what it does.
  • Error paths leak. Distinguishable failure messages hand an attacker information the success path never would.
  • Dependencies are attack surface. Every imported package is code you are trusting and are responsible for keeping current.

09 — Next

Future improvements

  • End-to-end encryption with forward secrecy — move key control to the clients so a server compromise cannot expose message history.
  • Multi-factor authentication — reduce the impact of credential compromise on account takeover.
  • Automated security testing in CI — dependency scanning and static analysis running on every change rather than on demand.
  • Independent review — have the cryptographic and authentication design examined by someone who did not write it.
  • Structured audit logging — record security-relevant events in a form that supports investigation without storing message content.
