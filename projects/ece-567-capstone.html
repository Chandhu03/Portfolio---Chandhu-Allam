01 — Overview

Overview

ECE 567 is my graduate capstone at the University of Victoria. The project brings artificial intelligence and machine learning techniques to bear on cybersecurity problems — specifically, how a system can learn to recognise malicious behaviour, and how that intelligence is designed into a system that is defensible in its own right.

The work deliberately treats two questions as one. Detection quality and system security are usually handled by separate teams; a model that classifies threats well but can itself be poisoned, evaded, or misread is not a security improvement. The capstone is structured so that both are examined together.

The principle guiding the work: machine learning earns its place only where it genuinely improves a security decision, not where it simply adds another component that has to be defended.

02 — Problem

Problem statement

Security teams receive far more telemetry than any group of analysts can triage by hand. Rule and signature based detection is precise and explainable, but brittle: it recognises what it has already been told to look for, and variants of known threats slip past it.

Machine learning offers generalisation to unseen behaviour, but brings its own costs. Models are opaque, they inherit every bias in their training data, false positives carry a real operational price, and the model itself becomes part of the attack surface. The problem this capstone addresses is not "can a classifier be trained" — it is how to apply learned detection in a way that a security engineer could actually justify and defend.

03 — Objectives

Objectives

  • Frame a security problem that genuinely benefits from learning rather than fitting a model to a problem a rule would solve better.
  • Build a reproducible pipeline from raw data through preparation, feature construction, training, and evaluation.
  • Compare candidate models on the same footing, including a simple baseline to establish whether complexity is earning its place.
  • Evaluate with security-appropriate measures — recall on genuine threats and the operational cost of false positives — rather than headline accuracy.
  • Document the threat model of the detection system itself, covering data poisoning, evasion, and the consequences of a wrong classification.
  • Communicate the result in a form a reviewer without a machine learning background can follow and challenge.

05 — Ownership

My role

This is my own capstone work, carried out within the ECE 567 course structure. I am responsible for the full arc of the project: framing the problem, reviewing prior work, selecting and preparing data, designing features, training and comparing models, designing the evaluation, analysing the security properties of the resulting system, and producing the written and spoken deliverables.

Where the course provides supervision and review checkpoints, the technical decisions and their justification are mine to make and defend.

06 — Approach

Implementation summary

The project runs in phases, each with a deliverable that the next phase depends on.

  • Scoping and prior work. Narrow a broad brief into a specific, testable detection problem, and establish what has already been tried.
  • Data preparation. Select representative data, clean it, and document every transformation so results can be reproduced.
  • Baseline first. Establish a simple, interpretable baseline before reaching for anything more complex, so later gains can be attributed.
  • Model comparison. Train candidate models under identical splits and preprocessing, tuning within the training data only.
  • Evaluation design. Choose metrics that reflect the cost of each error type in a security setting, and report confusion structure rather than a single number.
  • Security review. Step back and analyse the detection pipeline as an asset: what an attacker who knows it exists would target first.
  • Documentation. Consolidate methodology, results, and limitations into the capstone report.

07 — Friction

Challenges

Data that reflects reality

Security datasets are rarely balanced or current. Deciding what a dataset can honestly support a claim about — and where it cannot — shaped the scope more than any modelling choice.

Severe class imbalance

Genuine attacks are rare relative to normal traffic. A model that predicts "benign" for everything can look accurate while being useless, which forces careful metric selection.

Explaining a decision

A detection an analyst cannot interpret is a detection they cannot act on. Balancing model capability against explainability was a recurring trade-off.

Defending the model itself

Introducing a learned component introduces new attack surface — training data influence, evasion at inference, and over-trust in the output.

08 — Takeaways

Key learnings

  • Evaluation design is the real engineering. Choosing what to measure, and being honest about what the measurement does not cover, matters more than squeezing out another fraction of a point.
  • Baselines protect you. A simple model that performs comparably is a genuine result, not a failure — it tells you complexity is not warranted.
  • Security context changes the maths. The cost of a missed threat and the cost of a false alarm are not symmetric, and the metric has to reflect that.
  • Reproducibility is not optional. Documented data lineage and fixed random seeds are what make a result reviewable rather than anecdotal.
  • A model is a component, not a conclusion. It sits inside a system that also needs threat modelling, monitoring, and a defined failure mode.

09 — Next

Future improvements

  • Adversarial robustness testing — measure how the detection holds up against inputs deliberately crafted to evade it.
  • Concept drift handling — monitor for the degradation that follows when live traffic stops resembling the training distribution.
  • Streaming inference — move from batch analysis toward evaluation on live data with realistic latency budgets.
  • Explainability tooling — surface per-decision reasoning so an analyst can triage rather than simply trust.
  • Deployment hardening — treat the model artefact, its inputs, and its outputs as assets with their own access controls.
