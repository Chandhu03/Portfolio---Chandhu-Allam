01 — Overview

Overview

ECE 570 is a graduate digital forensics course built around hands-on investigations rather than theory alone. The work spans several distinct disciplines that share one requirement: whatever you conclude has to be supportable by evidence that has not been altered by the act of examining it.

Across the investigations I worked through malware behaviour analysis, memory image examination, incident response sequencing, and the acquisition and handling of evidence. Each one produced a written finding that had to stand up to being questioned.

Forensics taught me a discipline that transfers directly into engineering: separate what you observed from what you inferred, and never present the second as the first.

02 — Problem

Problem statement

Digital evidence is fragile in a way that physical evidence is not. Memory disappears at power-off, timestamps update when a file is opened, and a careless acquisition can destroy the very artefact being sought. At the same time, the analysis has to be thorough enough to reconstruct what actually happened.

Malware compounds the difficulty. Modern samples actively resist inspection — detecting virtual machines, obfuscating strings, delaying execution, and unpacking themselves only at runtime. The investigator's task is to characterise behaviour accurately without letting the sample escape containment or mislead the analysis.

03 — Objectives

Objectives

  • Acquire evidence without altering it, using verified imaging and hash-based integrity checks before and after acquisition.
  • Maintain a defensible chain of custody so that every artefact can be traced from source to finding.
  • Analyse volatile memory to recover process state, network activity, and injected code that a disk image alone would not reveal.
  • Characterise malware behaviour through both static inspection and controlled dynamic execution in an isolated lab.
  • Correlate artefacts into a timeline that explains a sequence of events rather than a list of disconnected observations.
  • Produce reports that separate fact from inference and state confidence honestly, including where evidence was inconclusive.

04 — Stack

Technologies used

Volatility

Memory image analysis — process listings, injected code, and network artefacts.

Autopsy / Sleuth Kit

Disk image examination, file system timelines, and deleted-file recovery.

Wireshark

Packet capture review and reconstruction of network behaviour.

Static analysis tooling

String extraction, header and import inspection, and hashing utilities.

Isolated VM lab

Snapshot-based sandbox for controlled detonation and rollback.

Linux

Command-line forensics utilities and scripted evidence processing.

05 — Ownership

My role

I carried out the investigations myself, from acquisition through analysis to the written finding. That included setting up and isolating the analysis environment, deciding acquisition order based on artefact volatility, running the examinations, and interpreting the results.

The reporting was as much a deliverable as the analysis. Each investigation had to be written so that another examiner could follow the method, reproduce the steps, and reach their own conclusion about whether mine was justified.

06 — Approach

Implementation summary

Every investigation followed the same sequence, which is the point — consistency is what makes findings comparable and defensible.

  • Prepare and isolate. Stand up a clean, network-isolated environment with snapshots so any change can be rolled back.
  • Acquire in order of volatility. Capture memory before disk, hashing the image immediately so integrity can be re-verified at any later point.
  • Triage. Establish scope quickly — what system, what timeframe, what question is actually being asked.
  • Examine memory. Recover running processes, loaded modules, network connections, and signs of injection or hollowing.
  • Examine storage. Build file system timelines, recover deleted artefacts, and inspect persistence locations.
  • Analyse the sample. Start static — strings, headers, imports — then move to controlled execution, observing changes against the clean snapshot.
  • Correlate and report. Assemble a timeline, mark each entry as observed or inferred, and document limitations.

07 — Friction

Challenges

Anti-analysis behaviour

Samples that detect a virtual machine, stall execution, or unpack only at runtime will show benign behaviour to a careless analyst. Recognising the absence of behaviour as a finding in itself took practice.

Volatility of evidence

Memory contents are gone the moment a system is powered down. Acquisition order is a decision made under time pressure, and getting it wrong is unrecoverable.

Correlating across sources

Disk, memory, and network artefacts each tell a partial story with their own clock. Reconciling them into a single defensible timeline was consistently the hardest part.

Containment discipline

Running live malware safely demands rigour about isolation, snapshots, and cleanup. One shortcut compromises both the lab and the credibility of the findings.

08 — Takeaways

Key learnings

  • Method is the deliverable. A correct conclusion reached through an undocumented process is not a usable finding.
  • Observation and inference are different things. Writing them in separate registers is what makes a report defensible under challenge.
  • Integrity checks are cheap and non-negotiable. Hashing at acquisition costs seconds and is the difference between evidence and an anecdote.
  • Absence of evidence needs stating. "I looked here and found nothing" is a result worth recording, not a gap to skip over.
  • Attacker perspective sharpens defence. Watching how malware establishes persistence changed how I think about hardening the systems I build.

09 — Next

Future improvements

  • Scripted acquisition — automate the repetitive parts of evidence collection to reduce the chance of human error under pressure.
  • Deeper reverse engineering — move from behavioural characterisation toward disassembly-level analysis of packed samples.
  • Timeline automation — build tooling that normalises timestamps across disk, memory, and network sources.
  • Detection feedback loop — translate observed indicators into detection rules, connecting forensics back to prevention.
  • Reporting templates — standardise the structure so findings stay consistent across investigations and investigators.
